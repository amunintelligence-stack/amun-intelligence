# MCP reference servers 2.0.0: 2026-07-28 spec era + legacy clients (Oct 19, 2026)

## What changed
- The MCP project released v2.0.0 of its official reference servers on Oct 19, 2026,
  eight days after v1.0.0 (AgentRiot, Oct 2026). TypeScript servers (filesystem,
  memory, sequential-thinking, everything) are 2.0.0 on npm and now REQUIRE Node 24;
  Python servers (fetch, git, time) are 2026.10.19 on PyPI.
- Every server now answers both eras from one process: the "modern" 2026-07-28
  revision (stateless, no `initialize` handshake, no session state) and the legacy
  2025-11-25 revision. Era selection is by first message: a `server/discover` request
  or 2026-07-28 per-request metadata starts a modern connection; an `initialize`
  request starts a legacy one. No server keeps state keyed by session ID anymore.
- Behavioral break to note: a 2026-07-28 client sending `ping` gets method-not-found,
  because that revision removes `ping`; 2025-era clients still get an answer.
- Context: v1.0.0 (Oct 11) added fetch's private-address guard (already recorded by
  the Oct 17 nightly as a default-deny pattern); v2.0.0 is described as the last
  legacy-era release line's successor, not a security patch.
- Parallel datapoint (telegra.ph, Oct 22, 2026): three protocol versions are live at
  once in the wild, and Red Hat's MCP gateway (GA Oct 16) negotiates 2025-03-26,
  2025-06-18, 2025-11-25 and 2026-07-28 on a single endpoint. The practical check the
  piece recommends: log the protocolVersion the server RETURNS, not the one you
  requested — a server answering 2025-06-18 to a 2026-07-28 request is correct
  negotiation, not failure.

## Why it matters for ACI
- ACI's MCP wiring is still planned, not built. The decision that matters now: any
  ACI MCP server built in future should target the 2026-07-28 stateless shape (and
  keep a legacy fallback only if a specific client needs it), because the reference
  line has moved there and Node 24 is now the TS floor.
- Adopt the logging rule now as a design rule for later: record returned
  protocolVersion per server, and treat `tools/list` stability (listChanged) as a
  monitored property — this dovetails with the Oct 22 "pin tool definitions / rug
  pull" guidance already in the registry.
