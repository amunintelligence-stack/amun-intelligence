# تأمين واستضافة خوادم MCP — Cloudflare Access + نمط AWS Fargate (7 نوفمبر 2026)

## Cloudflare Access — بوابات MCP (وثائق حُدّثت 2 نوفمبر 2026)
- **ما الذي تغيّر:** وثائق Cloudflare One توثّق الآن مسارين رسميين لتأمين خوادم MCP عبر Cloudflare Access:
  - **خادم يديره العميل:** خادم MCP لطرف ثالث يعمل على اسم مضيف تملكه، مع تدفق OAuth الخاص به — فعّل Proxy في DNS وأنشئ بوابة MCP (Zero Trust > Access controls > MCP Portals) وسياسات وصول تحدد المستخدمين المسموح لهم.
  - **خادم تديره SaaS:** مزود يستضيف خادم MCP ويدعم OAuth/OIDC مخصصًا — Cloudflare Access يعمل كموفر هوية OIDC، والخادم ينفذ تدفق authorization code ضده؛ ورموز تطبيق مرتبطة تتيح للخادم الوصول لتطبيقات مستضافة ذاتيًا أخرى نيابة عن المستخدم.
- **لماذا يهم ACI:** هذا هو النمط الجاهز إن عُرّضت خوادم MCP في ACI (الرسم/RAG) للخارج يومًا: هوية على الحافة قبل أن يصل أي طلب أداة إلى الخادم، بدل بناء مصادقة مخصصة. يتوافق مع قاعدة السجل الحالية (تثبيت `expectedIssuer` + بلا DCR + URLs مصدر دقيقة).
- **المصادر:** https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/secure-mcp-servers/ (حُدّث 2 نوفمبر 2026)
- **الإجراء: watch** — مرجع تصميمي لتعريض MCP البعيد المستقبلي؛ لا بناء بعد.

## AWS — خادم MCP بلا خادم على ECS Fargate لبوابة بحيرة بيانات (6 نوفمبر 2026)
- **ما الذي تغيّر:** نشرت AWS نمطًا مرجعيًا: خادم MCP على ECS Fargate كبوابة مركزية لوصول وكلاء الذكاء الاصطناعي إلى بحيرات بيانات المؤسسة — أربع طبقات (عميل/مصادقة، خادم MCP/تنسيق، أدوات SQL/بحث، تحديث قاعدة معرفة)، مع Cognito للمصادقة وWAF وBedrock Guardrails وفرض SELECT-only على الاستعلامات، وتوسع تلقائي عبر Fargate/Athena/Bedrock.
- **لماذا يهم ACI:** النمط المعماري قابل للاقتباس مباشرة: طبقة بوابة واحدة أمام مصادر بيانات متعددة + فرض قراءة فقط على مستوى البوابة (لا على حسن نية كل أداة) + حراسة على المدخلات/المخرجات. ACI يعمل محليًا، لكن إن انتقلت بوابة MCP إلى سحابة يومًا فهذا هو القالب — خصوصًا قاعدة SELECT-only كضمانة لا كسياسة.
- **المصادر:** https://aws-news.com/article/2026-11-06-serverless-mcp-server-for-ai-agent-data-lake-access-on-amazon-ecs-fargate (6 نوفمبر 2026)
- **الإجراء: watch** — مرجع معماري فقط.

## أدلة ترحيل MCP 2.0 — خلاصة (5–6 نوفمبر 2026)
- **ما الذي تغيّر:** ظهرت أدلة ترحيل لمواصفة 2026-07-28 («MCP 2.0» غير الرسمية): بلا حالة، بلا مصافحة initialize ولا رأس Mcp-Session-Id؛ طلبات متعددة الجولات بدل ردّات منتصف الطلب؛ تحقق إجباري من مصدر OAuth (`iss`)؛ تسجيل العميل الديناميكي مهمل لصالح مستندات بيانات Client ID؛ تطبيقات ومهام MCP تخرجتا من تجريبيتين إلى إضافتين رسميتين؛ سياسة إهمال: 12 شهرًا إشعارًا على الأقل (90 يومًا للأمن فقط). بايثون: الترقية إلى `mcp 2.x`، وإعادة تسمية `McpError` إلى `MCPError`، أو التثبيت على `mcp>=1.28,<2`.
- **لماذا يهم ACI:** يؤكد أن 2026-07-28 هو الأساس المستقر (والمواصفة التالية 30 مارس 2027 حسب SEP-3398)؛ أي خادم MCP جديد في ACI يُبنى على SDK 2.x بلا حالة منذ البداية.
- **المصادر:** https://dev.to/ali_82f3409ed625e8ba8515b/mcp-20-what-changed-and-how-to-migrate-5586 — https://arunkanish1998.medium.com/mcp-2-0-got-safer-it-also-handed-security-to-developers-80fb62babd40 (نوفمبر 2026؛ أدلة ثانوية تلخص المواصفة)
- **الإجراء: watch** — لا تغيير على خطة الأساس؛ سجّل قاعدة التثبيت `mcp>=1.28,<2` إن وُجد خادم على SDK 1.x.
